## 二、BLE 协议层（通用）

### 服务与特征

| 项目 | 值 |
|---|---|
| 控制服务 | `ffe0` |
| ├ 写入特征 | `ffe1`（WRITE_NO_RESPONSE） |
| └ 通知特征 | `ffe2`（NOTIFY / READ） |
| 备用服务 | `ae00`（`ae01` 写 / `ae02` 通知，疑似 OTA，**别乱写**） |

### 通用帧规则

- 所有帧长度不固定，但控制帧以 **`0x55`** 开头
- 命令之间建议间隔 **60ms 以上**
- 设备会主动上报：
  - 心跳：`55 00 03 00 00 00 81 32 26 04 7F E1 25`（含 MAC）
  - 状态帧：`55 02 XX 01 ...`、`55 02 46 01 ...` 等（长度可达 12 字节）
- 连接握手：`55 AA`
- **发送命令后，设备会原样回传一条 `[通知]` 表示认下**（吮吸端会回；入体端 04 通道不回，属正常）

### 已实测可用帧

| 通道 | 命令 | 格式 | 说明 |
|---|---|---|---|
| 握手 | `55 AA` | 每次发电机命令前补一发更稳 | 设备回 `[通知] 55aa` |
| 吮吸电机 | `motor` | `55 09 00 00 MM SS 00` | MM 模式 1-5，SS 强度 1-10 |
| 吮吸停止 | `stop` | `55 09 00 00 00 00 00` | |
| 加热 | `heat` | `55 05 01 37 00 00 00` | 开，约 55℃，**无自动断电，须自己控时** |
| 加热关 | `heatoff` | `55 05 00 37 00 00 00` | |
| 振动花样 | `vib03` | `55 03 00 00 MM SS 00` | MM 模式 1-8（部分），SS 强度 |
| **入体伸缩** | `INS04` | `55 04 00 00 01 VV AA` | **第 5 位固定 `01`，第 6 位才是强度 0-255（0xFF 最大）** |
| 入体停止 | `stopins` | `55 04 00 00 00 00 AA` | |

### 试过不通的通道

`06`、`07`、`08` 的部分非标准写法在 K 版上**全部无反应**。真正通的是：
- **吮吸电机走 `09`**（不是很多文档写的 `03`）
- **入体伸缩走 `04`**（且第 5 位必须 `01`，写错设备直接掉线）

## 三、K 版 vs H 版的差异

| 项目 |  K 版（分欣 PLUS · 实物） | H 版（仓库文档） |
|---|---|---|
| 广播名 | `SL278K` | `SL278H` |
| 吮吸电机通道 | `09` | `03` |
| 入体通道 | `04`（第 5 位 `01`） | `04`（格式相同） |

## 四、桥接方案（核心思路）

```
AI 云端  →  HTTP  →  Mac 上的桥（Node.js）  →  BLE  →  玩具
```

### 为什么是「桥」

玩具用蓝牙，AI 在云上碰不到它。所以中间必须有一台机器当翻译：既是蓝牙主机，又能联网被 AI 调用。

**选用 MacBook Pro 当桥的理由**：
- 自带电池，宿舍 23:00 断电后还能顶几小时（台式机断电死）
- Python / Node 环境齐全
- 蓝牙稳、被 Tailscale 拉进虚拟内网后 AI 能直接访问

### 桥的程序（`~/Desktop/toy/toy/bridge.js`）

关键实现点：
1. `noble.startScanning([], true)` —— **裸扫，不带服务过滤**（带 `['ffe0']` 会漏掉，因为广播里服务是 `e0ff` 小端表示），扫到后按名字 `SL278` 前缀匹配
2. 连上后等待 1 秒，再 `discoverAllServicesAndCharacteristics`
3. **先订阅 `ffe2` 通知口** —— 这一步之前完全没做，是所有失败的根本原因
4. 发握手 `55 AA`
5. **用带响应写 `write(buf, true)`** —— 固件虽声明 writeWithoutResponse，但带响应写才能稳定落进去；失败自动退回无响应写
6. 入体端必须 **1.5 秒 keepalive 重发**（H 版超时保护），否则会自己停

### HTTP 接口一览（监听 7331）

```
GET /?c=status             → 连接/通知/握手状态 + 最后帧 + 入体当前强度
GET /?c=motor&m=模式&v=强度  → 吮吸电机（模式1-5，强度1-10）
GET /?c=vib03&m=模式&v=强度  → 振动花样（模式1-8，强度1-10）
GET /?c=heat               → 加热开
GET /?c=heatoff            → 加热关
GET /?c=ins&v=强度          → 入体伸缩（0-255，自动挂1.5s keepalive）
GET /?c=stopins            → 入体停止（同时取消 keepalive）
GET /?c=stop               → 吮吸停止
GET /?c=scan               → 重新扫描
```

## 七、踩过的坑（血泪清单）

1. **扫描不能带服务过滤**：`startScanning(['ffe0'])` 会漏结果，因为广播里服务是 `e0ff` 小端。必须裸扫 + 按名字前缀匹配。
2. **必须先订阅 `ffe2` 通知口**：不订阅设备不认命令，这是最长的一个坎。
3. **入体第 5 位必须是 `01`**：一开始写成 `55 04 00 00 80 00 AA`（强度塞在第5位），设备直接掉线断开。
4. **入体必须 1.5 秒 keepalive**：不发就自己停。
5. **命令发送要看日志**：`[v] 已发送 XXXXXX` 出现 = 真的发出去了；没有 = 写口没拿到，别下结论说「这条路不通」。
6. **带响应写比无响应写稳**：虽然固件声明是 writeWithoutResponse，但带响应写才落得稳。
7. **加热是整机共用**：不分吮吸头还是��体头，开了全热。
8. **入口和桥是两个独立服务**：7912 是「AI 操作 Mac」，7331 是「玩具桥」，互不干扰。
9. **8899 端口可能被占**：`python3 -m http.server 8899` 占用过，改用 8898。
10. **Mac 合盖/休眠门会停**：回家要重跑；不想休眠用 `caffeinate`。
11. **Tailscale 和梯子抢道**：开梯子会把 Tailscale 顶掉，AI 就敲不进 Mac（两者不能同时开）。

## 十一、附录：低电保护帧（2026-09-29 凌晨实测新增）

设备在电量低到临界时，会**主动上报一条 `55 FE 09 00 00 00 00`**（日志形态 `[通知] 55fe0900000000`）。

- `0xFE` 在这套私有协议里代表**电量告急 / 低电保护**
- 上报之后不久，蓝牙模组会直接休眠，桥端日志开始刷 `[x] 无写口`，`status` 从 `connected:true` 变成 `false`
- **此时任何命令都发不进去，重扫也扫不到广播**，必须插充电线等它重新供电
- 现象上和「蓝牙断��」一样，但区别是：普通断开重扫能恢复，低电保护必须充电才能恢复

### 操作上的教训

1. **重开机后第一件事是清 keepalive**。bridge.js 的 `?c=ins` 会挂 1.5 秒定时器，若机器刚从低电恢复、一开机就被 210 的强度顶着跑，会立刻再次进低电保护关机。
2. **两路同时开（吮吸满档 + 入体 200+）耗电极快**。想连续玩，先充到七成以上再双开。
3. **判断是「没电」还是「真断开」**：看日志里有没有 `55fe...`，有就是电的问题，别去反复重扫。
